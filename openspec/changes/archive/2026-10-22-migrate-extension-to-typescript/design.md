# Design

## Context

动机、阅读审计和范围见 [proposal.md](proposal.md)。合并后基线 `e01840b` 中扩展为原生模块，49 个 JavaScript 文件含2411 行翻译目录。`scripts/check.mjs` 只检查 Manifest 资源及语法；`scripts/package.py` 直接压缩 `extension/`；CI 使用 Node 22，没有依赖安装步骤。

Manifest、HTML、`api.js` 的采集注入、`badge-observer.js` 的内容脚本与离屏/规则线程使用不同运行上下文。现有测试直接导入 `extension/*.js`；`language_test.py` 还将 `locales/catalogs.js` 的导出文本解析为 JSON（JavaScript Object Notation）。因此编译输出路径与该目录的数据文本形态必须兼容。

## Goals / Non-Goals

**Goals:** 全部扩展运行源码进入严格 TypeScript，明确跨模块数据、消息和浏览器接口的类型；保持可审阅的一对一模块迁移和现有加载路径；使干净安装、检查、测试及打包可重复执行。

**Non-Goals:** 不迁移 Python 工具或现有 JavaScript 测试，不添加框架、运行时依赖、权限、产品功能或存储迁移；不将缩略图视作原始文件；不修改既有测试用例或其运行逻辑。

## Decisions

### 1. 源码与生成脚本分离，保留扩展输出路径

将 `extension/**/*.js` 一对一迁为 `src/**/*.ts`，静态文件仍位于 `extension/`。新增 `tsconfig.json`，以 `src` 为根输出到 `extension`，保留源代码中的 `.js` 导入后缀。生成脚本从版本控制移除并加入忽略，`src` 是唯一脚本维护入口。构建只清理生成的脚本及关联编译文件，不删除 HTML、CSS、Manifest、翻译消息 JSON 或素材。

选择 TypeScript 编译器直接输出原生模块，不引入捆绑器（Bundler）：当前浏览器原生支持模块，注入脚本依赖独立可序列化函数，捆绑可能引入闭包辅助函数。编译目标采用 Chrome 116 支持的现代 JavaScript，保留异步和原生类等语义；内容脚本和采集脚本保持可直接注入，不产生运行时 import/export。若仅为类型共享需要引用模块，使用纯类型导入并验证输出不会生成模块语法。

### 2. 严格检查和显式边界

开发依赖固定 TypeScript 与 Chrome 类型声明版本，提交锁文件。启用 `strict`、`noEmitOnError`、未使用宽松 JavaScript 回退；不通过关闭检查、跳过项目类型错误或增加宽松声明逃避迁移。编译环境按 DOM、工作线程（Web Worker）和后台实际用途处理，避免同时加载相互冲突的全局库。

为图片候选、来源、读取结果、下载结果、阈值及覆盖、远程规则、订阅、同步载荷/版本和消息定义共享契约。使用 Chrome 官方生态类型和必要的本地接口描述文件系统能力、页面注入全局及自定义事件。外部消息、存储、调试协议和 JSON 结果先作为 `unknown`，用现有校验或等价类型守卫（Type Guard）收窄；不新增改变兼容性的业务拒绝规则。

遵循 AGENTS.md：禁止类型断言、显式 `any`、非空/确定赋值断言和检查抑制注释。维护者检查入口使用编译器抽象语法树（Abstract Syntax Tree, AST）检查项目自有 TypeScript 的禁用语法；合法导入别名不误报。第三方声明不手改，不把其宽类型未经检查传入项目逻辑。

### 3. 开发、检查与发布共用成功构建

新增 `npm run build` 与 `npm run typecheck`。`npm run check` 包含类型与类型安全规则检查、构建及完整资源校验；`npm test` 在运行原测试前构建；`npm run package` 先检查和构建，再压缩。构建先验证类型，任何失败非零退出；不以磁盘已有输出证明成功。

检查脚本扩充本地资源关系验证，覆盖 Manifest、HTML、模块导入、脚本注入、离屏页和线程入口。ZIP 仍为 `dist/imagetaken-<version>.zip`，根目录含 Manifest，排除 `.ts`、声明、源码映射（Source Map）、开发依赖和测试。CI 先 `npm ci`，再按检查、单元、浏览器和打包入口执行。README 区分克隆源码需先构建与发布 ZIP 可直接加载；更新开发文档及 `openspec/config.yaml` 中的源码/构建描述，避免留下“无需构建”承诺。

### 4. 保留全部现有测试，补充交付操作证据

盘点及零测试修改范围见 proposal。通过保留 `extension/` 输出确保 18 个 Node 文件的导入、10 个浏览器脚本及现有 CI 仍可使用；不改测试数据、断言、快照或查找浏览器方式。翻译目录的输出必须继续满足 `language_test.py` 的 JSON 读取契约。

实施验证使用原测试，另在临时目录进行干净依赖安装/构建/打包、临时引入类型错误与缺失资源的失败检查，以及删除模块后清理输出的操作验证；这些是交付验证命令，不写入或修改测试用例。核对包内文件及解压后的真实浏览器入口。macOS 专用浏览器脚本无法在当前 Linux 环境直接运行时记录其边界，使用临时浏览器配置补充对应入口的实跑证据，不把补充检查声称为原脚本通过。若实现确实要求变更任何用例，停止该部分并先提出完整逐项审批。

## Risks / Trade-offs

- 注入函数引用被编译引入的模块闭包 → 使用现代目标、一对一输出和纯类型依赖，检查注入输出并在真实浏览器验证。
- 类型收窄意外改变容错行为 → 复用既有校验，保持原边界和回退；回归配置、图片数据及规则同步。
- 遗留 JavaScript 掩盖缺失产物 → 构建清理生成脚本，干净检出和失败构建单独验证。
- DOM、线程及 Chrome 事件边界类型冲突 → 按上下文设置类型，显式定义必要接口，不放宽检查器。
- 编译后的翻译文件不满足文本解析 → 检查生成文本兼容性，保持数据对象直接导出的格式，不放宽原测试。
- 首次源码加载新增工具安装 → README 给出 `npm ci`、构建和重新加载步骤；发布 ZIP 用户维持直接加载。
- 部分浏览器脚本硬编码 macOS 缓存 → 如实报告不可执行项与补充证据，不自行修改用例或误报成功。

## Migration Plan

审批后先记录有效批准，建立构建和共享类型，再逐模块迁移，保持产品语义。全部类型与资源检查通过后运行原单元/浏览器验证及临时目录交付检查，同步文档和规格，归档并按仓库规则自动提交。回退以恢复本次迁移前代码和开发步骤实现，无配置或用户数据回滚需要。

`External-Skill: exempt`，`README-Glossary: verified`：依据 proposal 中的候选、分发与术语审计；新增构建能力只影响维护者安装流程，无项目私域概念或消费方 Skill 变化。
