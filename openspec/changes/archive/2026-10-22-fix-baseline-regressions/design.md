# Design

## Context

动机与冲突决定见 [proposal.md](proposal.md)。原 `e01840b` 与类型迁移输出在相同 Linux Chromium 151 环境中均复现三处失败。此阶段只完成规划；不能把同样复现等同于已证明根因，也不能以旧代码行为改写规格。

| 失败证据 | 直接路径与当前判断 | 约束来源 |
| --- | --- | --- |
| `browser_test.py::test_settings` 第354行，勾选后立即重载，期望开启而实际关闭 | 设置页异步调用 `saveConfig`，配置写入互斥（Web Locks）运行在发起视图；重载与排队写入存在竞争，需用存储及锁的时序确认 | `user-preferences` 分类设置与即时保存、成功图片优先默认开启；配置同步归档保留原子写入与跨视图一致性 |

阅读按 Requirement/Scenario、失败用例、配置键、函数与文件路径检索。依据包含完整的 `user-preferences`、`image-data`、`image-library` 主规格；`2026-10-22-chrome-settings-sync` 和 `2026-10-22-multi-source-image-extraction` 的方案、设计、任务与相关增量；继承 `highlight-selected-source-images` 的方案、设计、任务与两份增量。沿用本机优先保存、配置写入互斥、原图与静态缩略像素隔离、临时 Referer 规则精确匹配及清理、原页元素映射不跨消息传引用等历史决策。

## Goals / Non-Goals

**Goals:** 恢复三组现有回归覆盖的规格行为；修复需落在共享行为源头，保留其他视图、并发请求、授权和导航隔离约定；验证后使类型迁移可继续验收。

**Non-Goals:** 不迁移存储格式、不改默认配置或权限、不增加依赖，不通过延长超时、修改断言、跳过用例或关闭功能解决失败；不重做类型迁移、不把猜测的根因当作完成证据。

## Decisions

### 1. 设置保存交由生命周期稳定的后台完成

先复现并记录开关事件、锁申请、存储写入与页面退出的顺序。将共享开关已发起的保存请求交由服务工作线程（Service Worker）校验并完成，复用同一配置写入锁与现有存储接口。消息必须限制受信扩展设置页、白名单配置键和布尔值；响应表示实际写入结果，设置页沿用禁用中、失败恢复和保存成功反馈。重载后的页面读取最终持久化值并接受存储变更。

避免让设置页持有锁后再等待同锁后台请求而死锁。优先复用后台现有串行写入模式，不引入新存储键或延迟保存期限。单纯在测试重载前等待会掩盖已发起请求随视图消失的问题，不属于本次方案。

### 2. 请求去重以一次完整提取任务为边界

利用临时运行日志核对请求发起者、资源目标、Referer 和任务代次，区分页面原有请求与扩展新请求，不只比较汇总数字。重点排查预览直接地址加载和主动读取并行，以及重新扫描触发失败任务重置。将扩展引发的同次原文件读取归入已有共享任务，HTTP 普通及来源回退继续由后台请求管理器统一调度；成功完整原图供预览和下载复用，失败仅按已有主动重试/换源/重新扫描规则重试。

保持 Data URL、页面 Blob、Canvas、静态像素预览的独立契约，不能把静态预览缓存当作原文件，也不能牺牲正常显示、原格式下载或请求隔离换取更低计数。保留跨地址并发限制、精确临时规则、清理失败阻断、签名地址和网站调试授权。若证据显示失败来自浏览器版本行为而非扩展重复请求，记录差异并再次执行冲突门禁，不自行放宽测试。

### 3. 高亮释放必须具备独立于绘制调度的完成路径

先确认取消操作确实改变实际选择，以及空快照是否送达。按定位结果修复选择通知或释放链路，确保最新空选择进入串行协调器并释放该视图拥有的全部文档会话；普通释放不依赖十五秒异常过期。连接关闭与正在注入的更新通过同一队列和序号防止旧会话重建，必要时让后台确认已接受释放后再关闭客户端连接。绘制层清理仅按自身会话，不清除其他图库会话。

继承高亮 change 由默认分支引入，原任务尚未全部勾选。本修复语义与其相关，不能当作无关遗留项绕过。实施前核对其已有测试审批记录和实现证据；本次不重新创建其16个已存在用例，不自动修改它们。验证涵盖其 HU01–HU04、HB01–HB12 及相关已有回归，验收事实足够后才能记录完成并处理相关归档。

### 4. 分支与类型迁移整合

该独立工作区仅保存提案，基线未含类型迁移。修复获批后在此分支按现有源码布局实施，验证后将修复映射合入原迁移的 `src/`（不得恢复生成 JS 的版本控制）；再次运行严格类型、构建及全量回归后才结束迁移。修复与迁移分别保留审计和提交归属，不把一方尚未通过的结果视为另一方已验收。

若选择直接在类型源码上实施，应先将迁移的完整工作树快照带入独立分支并记录基线，禁止手工复制/改名活跃 change 来释放名额。任何最终方案改变须按仓库审批规则更新，不在规划阶段执行整合。

## Risks / Trade-offs

- 浏览器回归目前在首个失败处结束 → 实施后必须继续跑完整脚本，后续新失败需重新定位，不能只修三个断言就宣称完成。
- 写入移到后台可能扩大消息入口 → 严格校验来源、白名单和值，沿用配置锁，检查云端失败不阻断本机保存。
- 请求去重可能改变失败重试或预览时机 → 用原提取、图片数据、下载及徽标测试验证完整字节、请求次数、并发及取消。
- 等待高亮释放可能延迟断连 → 只等待有界操作，关闭/导航仍有后台释放与异常到期兜底；不把十五秒兜底当作一秒正常行为。
- 原测试后续发现需要变更 → 立即停止该部分，逐项完整盘点并请求用户确认，不用当前“零测试修改”提案批准绕过。

## Migration Plan

审批当前 proposal、三份 delta、design 和 tasks 后进入 Apply。依次定位并修复设置保存、提取请求与高亮清理，按原测试验证，补文档和证据；完成相关继承 change 的验收后再同步主规格与归档。随后整合类型迁移并重新验证，按各 change 的实际关联执行提交门禁。无用户数据迁移，回退恢复对应实现；不自动发布或推送。
